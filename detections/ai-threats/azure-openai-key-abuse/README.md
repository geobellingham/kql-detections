| **ATT&CK** | T1552.005 Cloud Instance Metadata / credentials, T1562 Impair Defenses, T1496 Resource Hijacking |
| **Severity** | Medium, High when the content filter changed and keys were read by someone new or traffic spiked |
| **Runs** | Hourly, 14-day query period |

## Goal
Catch LLMjacking on Azure: someone gets an Azure OpenAI key, loosens the content filters and uses up the quota from their own machines.

## How it works
The signals are combined per Cognitive Services account, so one alert covers everything that happened to it:

| Signal | Points | Source |
|---|---|---|
| Content filter (RAI policy) or blocklist changed or deleted | 4 | `…/RAIPOLICIES/WRITE`, `…/RAIPOLICIES/DELETE`, `…/RAIBLOCKLISTS/DELETE`, `…/DELETERAIBLOCKLISTITEMS/ACTION` |
| Keys listed or regenerated by an identity that hasn't done it in 13 days | 2 | `…/LISTKEYS/ACTION`, `…/REGENERATEKEY/ACTION` |
| Request spike: 200+ requests this hour and more than 5 times the busiest baseline hour | 2 | `AzureDiagnostics` RequestResponse |
| Requests from /24 ranges the account has never had traffic from | 2 | `CallerIPAddress` prefixes |
| Key regenerated | 1 | |
| 50+ client errors (4xx) from new ranges, i.e. someone testing keys | 1 | `ResultSignature` |

The alert fires at 4 or more, so a content filter change alone is enough. Child resource IDs (`…/raiPolicies/x`) are trimmed back to the parent account so the control-plane and data-plane events match up.

## Technical context
- Request logs only exist if a diagnostic setting sends the account's `RequestResponse` category to the workspace. All Azure OpenAI log categories go to `AzureDiagnostics`.
- `CallerIPAddress` often has the last octet masked, so ranges are compared at /24.
- `listKeys` also happens when someone opens the Keys and Endpoint page in the portal. Reading keys on its own is normal, so it's only worth 2 points and only for identities that haven't done it before.

## Blind spots
- Accounts that only allow Entra ID auth, with keys disabled. There's no key to steal. Stolen managed identity tokens look like normal traffic from the app's own IP, so only the spike signal is left.
- Abuse coming from the same network as your own app.
- Prompt content. For jailbreak and prompt injection signals, use the Defender for Cloud AI threat protection alerts in `SecurityAlert`, which could be added to the score.

## False positives
- Platform teams tuning content filters while onboarding. Expect alerts in the first few weeks. After that, put filter changes through a change process.
- Load tests or batch jobs from a new build agent range: spike plus new range scores 4. Check with the app owner.

## Validation
- **Sample data:** `node tools/render-test.js azure-openai-key-abuse`. Expected result: one row for `aoai-prod`, score 11, High. `aoai-dev`, with normal traffic, doesn't show up.
- **Test subscription:** list the keys as a new user, edit the content filter, and send a few hundred requests from a different network with `curl`.

## Response
1. Regenerate both keys, since the attacker has one, and update your own apps. Think about turning off local auth and moving to Entra ID.
2. Undo the content filter or blocklist change and check who made it (`GuardrailCallers`, `GuardrailIPs`). If it wasn't planned, treat that identity as compromised.
3. Check usage and cost for the period, and look for new deployments created around the same time (`…/DEPLOYMENTS/WRITE`). Attackers sometimes add a model deployment for themselves.
