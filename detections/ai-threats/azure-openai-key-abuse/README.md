# Azure OpenAI / Foundry key theft, guardrail tampering or request spike

| | |
|---|---|
| **Rule** | [`rule.yaml`](rule.yaml) · test: [`tests/fixtures/azure-openai-key-abuse.kql`](../../../tests/fixtures/azure-openai-key-abuse.kql) |
| **Data** | `AzureActivity` (control plane), `AzureDiagnostics` with the `RequestResponse` category (data plane) |
| **ATT&CK** | T1552.005 Cloud Instance Metadata / credentials, T1562 Impair Defenses, T1496 Resource Hijacking |
| **Severity** | Medium; **High** when guardrails were changed *and* keys were read by someone new or traffic spiked |
| **Runs** | Hourly, 14-day query period |

## Goal
Catch the Azure version of LLMjacking: someone obtains an Azure OpenAI key, weakens the content filters, and burns the quota from their own infrastructure.

## Strategy
Signals are joined **per Cognitive Services account**, so one alert tells the whole story:

| Signal | Points | Source |
|---|---|---|
| Content filter (RAI policy) or blocklist written/deleted | 4 | `…/RAIPOLICIES/WRITE`, `…/RAIPOLICIES/DELETE`, `…/RAIBLOCKLISTS/DELETE`, `…/DELETERAIBLOCKLISTITEMS/ACTION` |
| Keys listed or regenerated by an identity not seen doing it in 13 days | 2 | `…/LISTKEYS/ACTION`, `…/REGENERATEKEY/ACTION` |
| Request spike: ≥ 200 requests this hour and > 5× the busiest baseline hour | 2 | `AzureDiagnostics` RequestResponse |
| Requests from /24 ranges the account has never served | 2 | `CallerIPAddress` prefixes |
| Key regenerated | 1 | |
| ≥ 50 client errors (4xx) from new ranges, i.e. someone testing keys | 1 | `ResultSignature` |

Alert at **≥ 4**, so a guardrail change alone is enough. Child resource IDs (`…/raiPolicies/x`) are normalised to the parent account so control-plane and data-plane events line up.

## Technical context
- Request logs only exist if a **diagnostic setting** sends the account's `RequestResponse` category to the workspace. All Azure OpenAI log categories go to `AzureDiagnostics`.
- `CallerIPAddress` is often partially masked (last octet), which is why ranges are compared at /24.
- `listKeys` also happens when someone opens the **Keys and Endpoint** blade in the portal. Reading keys isn't malicious by itself, which is why it scores 2 and only for identities that haven't done it before.

## Blind spots
- Accounts using **Entra ID auth only** (keys disabled): key theft is impossible. Token theft for a managed identity shows up as normal traffic from the app's own IP, so only the spike signal remains.
- Abuse from the same egress the legitimate app uses (attacker inside the app's network).
- Prompt content. For jailbreak / prompt-injection signals use Defender for Cloud **AI threat protection** alerts (`SecurityAlert`), which can be added to the score.

## False positives
- Platform teams tuning content filters during onboarding. Expect alerts in the first weeks, then add their identities to a change process rather than an exclusion.
- Load tests or batch jobs from a new build agent range: spike plus new range = 4. Check with the app owner.

## Validation
- **Synthetic:** `node tools/render-test.js azure-openai-key-abuse`. Expected: one row for `aoai-prod`, score 11, High. `aoai-dev` (normal traffic) stays silent.
- **Live, test subscription:** list keys as a new user, edit the content filter, and send a few hundred requests from a different network with `curl`.

## Response
1. **Regenerate both keys** (the attacker has one) and update the legitimate apps. Consider disabling local auth and moving to Entra ID.
2. Revert the content filter / blocklist change and review who made it (`GuardrailCallers`, `GuardrailIPs`). Treat that identity as compromised if it wasn't a planned change.
3. Check usage and cost for the period. Look at deployments created around the same time (`…/DEPLOYMENTS/WRITE`), since attackers sometimes add a new model deployment for themselves.
